How the Compliance Scraping & Ingestion Pipeline Works

A walk-through of how GDPR / EU AI Act / DPDP legal text gets from a public website into MongoDB, and how a chat query later finds the right clause — with the real code from this project.

1. The big picture (two pipelines) 2. Fetching the page (fetch()) 3. Parsing HTML with Cheerio 4. Extracting clean, structured data 5. Writing the intermediate JSON file 6. Turning text into vectors (embeddings) 7. Storing in MongoDB (the upsert) 8. Query time: vector search + reranking 9. Glossary

1The big picture

There are really two separate pipelines that run at completely different times:

Ingestion pipeline — runs once, offline, whenever you click "Scrape Articles" → "Embed & Store"
🌐
1. Public website
gdpr-info.eu / dpdpa.com / artificialintelligenceact.eu — one page per article/section
↓ fetch(url)
📄
2. Raw HTML text
Just one big string — everything the browser would parse, unparsed
↓ cheerio.load(html)
🔍
3. Queryable DOM (Cheerio)
Now you can ask for elements by CSS selector, like jQuery — but no browser, no JavaScript execution
↓ $('.entry-content').children('ol,p,ul')...
✂️
4. Extracted fields
{ standard, clauseId, title, text, url } — one object per article/section
↓ fs.writeFileSync(...)
🗂️
5. Local JSON file
src/data/compliance/gdpr-clauses.json — a checkpoint before spending API money
↓ MistralAIEmbeddings.embedDocuments(...)
🧮
6. Embedding vectors
Each clause's text becomes a list of 1024 numbers capturing its meaning
↓ collection.bulkWrite(upsert by clauseId)
🍃
7. MongoDB Atlas
Stored as a document with the vector attached; Atlas builds a Vector Search index over it
Retrieval pipeline — runs every time someone searches in the chat UI
💬
1. User types a story
e.g. "User can request full deletion of their account and data"
↓ embeddings.embedQuery(story)
🧮
2. The story becomes a vector too
Same embedding model as ingestion — otherwise the numbers wouldn't be comparable
↓ $vectorSearch aggregation (cosine similarity)
📋
3. Top-K candidate clauses
The clauses whose vectors are numerically closest to the story's vector
↓ LLM reranking (Mistral/Gemini judges real relevance)
⭐
4. Ranked matches with scores
Reordered by how relevant the clause actually is, 0–1, nothing silently dropped
↓ render as a table
🖥️
5. Chat UI — Compliance Matches table
Clause / Relevance / Excerpt / Link
Why two separate pipelines? Ingestion is slow and costs API calls (scraping 99–113 pages, embedding each one) — you only want to do it when the source text actually changes. Retrieval has to be fast (a few seconds), so by query time everything is already pre-computed and sitting in MongoDB, ready to compare against.

2Fetching the page — fetch()

fetch() is a built-in JavaScript function (no library needed) that makes an HTTP request to a URL and gives you back the response. It's the exact same thing your browser does when it loads a page — except here, nothing gets displayed. You just get the raw text back.

src/scripts/gdprScraper.js 
async function fetchArticle(n) {
  const url = `${BASE_URL}/art-${n}-gdpr/`;
  const res = await fetch(url, { headers: { "User-Agent": "Mozilla/5.0" } });
  if (res.status === 404) return null;
  if (!res.ok) throw new Error(`Fetch failed for ${url} (HTTP ${res.status})`);

  const html = await res.text();   // <-- this is the entire page's HTML, as one big string
  ...
}
PieceWhat it means
await fetch(url)Sends the HTTP request and waits for the server to respond. await is needed because network calls take time — the code pauses here without blocking anything else.
User-Agent headerIdentifies the request as coming from "a browser" — some sites reject requests with no User-Agent, treating them as bots.
res.status === 404Some article numbers might not exist (or might 404) — handled as "skip it," not "crash the whole scrape."
await res.text()Reads the response body as plain text. At this point it's still just a string — nothing has been parsed or understood yet.
Being a considerate scraper. Between each article, the scraper waits 1 second (await sleep(REQUEST_DELAY_MS)) instead of firing 99+ requests at once. Real people run these websites — hammering them with concurrent requests is inconsiderate and can look like an attack.

The DPDP scraper has an extra step: discovery

GDPR and EU AI Act articles live at predictable URLs (/art-17-gdpr/, /article/17/) — you can just loop n = 1..99. DPDP's site nests URLs under a chapter number that isn't guessable from the section number alone (e.g. Section 18 lives at /chapter-5/section18.html). So dpdpScraper.js first fetches the site's own homepage and discovers every real section→URL mapping from its navigation links, before fetching each one:

src/scripts/dpdpScraper.js 
async function discoverSectionUrls() {
  const res = await fetch(INDEX_URL, ...);
  const html = await res.text();
  const pattern = /https:\/\/(?:www\.)?dpdpa\.com\/dpdpa2023\/chapter-\d+\/section(\d+)\.html/g;
  const bySectionNumber = new Map();
  let match;
  while ((match = pattern.exec(html))) {
    bySectionNumber.set(Number(match[1]), match[0]);
  }
  return [...bySectionNumber.entries()].sort((a, b) => a[0] - b[0]).map(([, url]) => url);
}

3Parsing HTML with Cheerio

Once you have the raw HTML string, you need a way to ask questions about it — "give me the element with class dsgvo-title", "give me every <li> inside this list". A plain string can't answer that; you need something that understands HTML's tree structure.

Cheerio is a lightweight library that parses an HTML string into a tree of elements and gives you a jQuery-like API to query and manipulate it — the same $('.some-class') selector syntax jQuery made popular, but running on the server in plain Node.js, with no real browser involved. That's the key distinction from something like Puppeteer/Playwright:

CheerioA real headless browser (Puppeteer, etc.)
What it isAn HTML parser + jQuery-style query APIAn actual browser engine running without a visible window
Runs JavaScript on the page?NoYes
SpeedVery fast, low memoryMuch slower, heavier
When you need itThe content is already in the HTML (server-rendered)The content only appears after JS runs (client-rendered SPA)

All three legal-text sites here render their content directly in the HTML (view-source shows the real text), so Cheerio is the right, lightweight tool — no need to pay the cost of a full browser.

src/scripts/gdprScraper.js 
const cheerio = require("cheerio");
...
const html = await res.text();
const $ = cheerio.load(html);   // <-- parses the string into a queryable tree

const h1 = $("h1.entry-title").first();
const clauseId = h1.find(".dsgvo-number").text().trim();   // "Art. 17 GDPR "
const title = h1.find(".dsgvo-title").text().trim();       // "Right to erasure ('right to be forgotten')"

cheerio.load(html) returns a function conventionally named $ (same convention as jQuery). Calling $("selector") finds matching elements anywhere in the parsed document, exactly like document.querySelectorAll() would in a browser.

The Cheerio methods actually used in this project

MethodWhat it does
$(".class")Find all elements matching a CSS selector, anywhere in the document.
.first()Narrow a multi-element match down to just the first one.
.find("li")Search only inside the current element(s) for descendants matching the selector (includes nested ones, at any depth).
.children("ol, p, ul")Like .find(), but only direct children — doesn't reach into grandchildren. Used to grab exactly the top-level paragraphs/lists of an article body.
.text()Get the plain-text content of an element, with all HTML tags stripped — but it recurses into every descendant's text too.
.clone()Make an independent copy of an element, so you can modify the copy (e.g. delete parts of it) without touching the original parsed document.
.remove()Delete matched elements entirely from the tree they're in.
.each((i, el) => ...)Loop over every matched element, like Array.forEach.

4Extracting clean, structured data

This is the part that took the most iteration in this project — real websites are messy, and .text()'s "recurse into everything" behavior causes real bugs if you're not careful. Two concrete ones this scraper had to solve:

Bug 1: nested lists get duplicated

GDPR Article 20 has a point with two lettered sub-points nested inside it:

<li>...personal data..., where:
  <ol>
    <li>the processing is based on consent...</li>
    <li>the processing is carried out by automated means.</li>
  </ol>
</li>

Calling .text() on the outer <li> returns its own text plus the nested list's text, all concatenated — and then looping over every <li> (via .find("li")) visits the nested ones again, so their text appears a second time. The fix: clone each <li>, remove any nested <ol>/<ul> from the clone first, then read its text — so you get each item's own words exactly once, in the right order.

src/scripts/gdprScraper.js 
$el.find("li").each((_j, li) => {
  const $li = $(li).clone();          // work on a copy, not the real parsed tree
  $li.find("ol, ul, sup").remove();   // strip nested lists (see bug 2 for "sup")
  const text = cleanText($li.text()); // now this li's OWN text only
  if (text) parts.push(text);
});

Bug 2: citation markers glue onto the next word

Some GDPR paragraphs use a superscript number to pinpoint-cite an individual sentence, with zero whitespace in the source markup:

<li><sup>1</sup>The exercise of the right... <sup>2</sup>That right shall not apply...</li>

Read as plain text, that becomes the confusing "1The exercise... 2That right..." — readable to a citation-aware human, but visually like stray typos to anyone else. The fix: remove <sup> elements from the clone before extracting text, same idea as the nested-list fix above.

Same root cause, same fix shape. Both bugs come from .text()'s "grab everything underneath, whether you wanted it or not" behavior. The general pattern — clone() → remove() the parts you don't want → then .text() — is reusable any time HTML mixes "real content" with "annotations you don't want."

5Writing the intermediate JSON file

After all articles/sections are fetched and cleaned, the scraper writes one JSON array to disk, e.g. src/data/compliance/gdpr-clauses.json: 

[
  {
    "standard": "GDPR",
    "clauseId": "Art. 17 GDPR",
    "title": "Right to erasure ('right to be forgotten')",
    "text": "The data subject shall have the right to obtain...",
    "url": "https://gdpr-info.eu/art-17-gdpr/"
  },
  ...
]

This file is a deliberate checkpoint between two very different kinds of work:

  • Scraping is free and safe to re-run as many times as you want — it just re-fetches public pages.
  • Embedding (next step) costs real API calls to Mistral, and writes to a shared database.

Splitting them means you can inspect the scraped JSON, confirm it looks right, and only then spend the API budget embedding it — instead of finding out something scraped wrong only after it's already in the database.

6Turning text into vectors (embeddings)

An embedding is a list of numbers (here, 1024 of them) that represents the meaning of a piece of text, produced by a machine-learning model (Mistral's embedding model, in this project). Two pieces of text with similar meaning get numerically close vectors — even if they don't share any of the same words. That's what makes it possible to search by "this story is about deleting personal data" and find "Art. 17 — Right to erasure," without either text literally containing the word "delete."

src/scripts/complianceIngest.js 
const embeddings = new MistralAIEmbeddings({ apiKey: MISTRAL_API_KEY, model: MISTRAL_EMBEDDING_MODEL });

async function embedTexts(texts) {
  const vectors = await embeddings.embedDocuments(texts);   // one 1024-number array per input text
  ...
  return vectors;
}

Each clause is embedded as title + "\n" + text (not just the body text alone) — so a query that closely echoes a clause's own title isn't invisible to the embedding just because the title only lives in metadata.

7Storing in MongoDB (the upsert)

Each clause becomes one MongoDB document, embedded in batches of COMPLIANCE_INGEST_BATCH_SIZE (default 20) so a single Mistral API call doesn't have to carry the whole collection at once:

src/scripts/complianceIngest.js 
const ops = batch.map((clause, idx) => ({
  updateOne: {
    filter: { clauseId: clause.clauseId },     // find by clauseId...
    update: {
      $set: {
        standard: clause.standard,
        clauseId: clause.clauseId,
        title: clause.title,
        text: clause.text,
        url: clause.url,
        embedding: vectors[idx],               // ...the 1024 numbers from Mistral
        metadata: { standard: clause.standard, clauseId: clause.clauseId },
        updatedAt: now,
      },
      $setOnInsert: { createdAt: now },
    },
    upsert: true,                              // ...update if found, INSERT if not
  },
}));
await collection.bulkWrite(ops);

upsert: true means "update this document if one with a matching clauseId already exists, otherwise create it." That's what makes re-running ingestion safe: scrape and embed the same article twice, and the second run just overwrites the same document instead of creating a duplicate.

The metadata.standard / metadata.clauseId fields exist specifically because the MongoDB Atlas Vector Search index (a separate thing you configure in Atlas, not created by this code) is defined to filter on those exact nested paths — the index definition and the document shape have to agree with each other.

8Query time: vector search + reranking

When someone searches with a story, three things happen in sequence:

  1. Embed the story — the exact same embedding model turns the user's story into its own 1024-number vector.
  2. Vector search — MongoDB's $vectorSearch aggregation stage compares the story's vector against every stored clause's vector using cosine similarity (a measure of how closely two vectors "point in the same direction"), and returns the closest matches.
  3. LLM reranking — vector similarity alone is a rough signal. The candidates get sent to the chat model (Mistral or Gemini, whichever CHAT_MODEL_PROVIDER selects) with a prompt asking it to actually judge relevance and assign a 0–1 score to each — reordering the list without silently dropping anything.
src/scripts/complianceClauseRetriever.js 
const candidates = await collection.aggregate([
  {
    $vectorSearch: {
      index: indexName,
      path: "embedding",
      queryVector,           // the story's own vector
      numCandidates,
      limit,
      filter: { "metadata.standard": standard },
    },
  },
  { $project: { _id: 0, clauseId: 1, title: 1, text: 1, url: 1, score: { $meta: "vectorSearchScore" } } },
]).toArray();

The result is what the chat UI renders as the "Compliance Matches" table — clause, relevance score, an excerpt of the actual legal text, and a link back to the source page.

9Glossary

HTTP fetch
Asking a server for a resource (here, a web page) and getting its content back as a response.
HTML parsing
Converting a raw HTML string into a structured tree of elements you can navigate and query, instead of just text.
DOM (Document Object Model)
The tree structure a parsed HTML document forms — elements nested inside other elements.
CSS selector
A pattern like .entry-content or h1.entry-title used to pick out specific elements from a DOM tree.
Cheerio
A Node.js library that parses HTML and exposes a jQuery-like selector API, without running a real browser or executing JavaScript.
Scraping
Automatically fetching and extracting data from web pages, as opposed to a human reading them.
Embedding
A numeric vector representing the meaning of a piece of text, produced by a machine-learning model, positioned so that similar meanings end up numerically close together.
Vector search
Finding the stored vectors that are numerically closest to a query vector — the mechanism behind "search by meaning" instead of "search by matching keywords."
Cosine similarity
A way of measuring how similar two vectors are by the angle between them, regardless of their length — the standard comparison used in vector search.
Reranking
A second pass over a shortlist of candidates (usually done by an LLM) that judges their real relevance more carefully than the fast first-pass similarity search could.
Upsert
"Update if it exists, insert if it doesn't" — a single database operation that makes re-running the same write idempotent (safe to repeat).
Idempotent
Running the same operation multiple times has the same effect as running it once — no duplicates, no extra side effects.
