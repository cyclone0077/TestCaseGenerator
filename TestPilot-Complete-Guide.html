TestPilot — Complete Architecture Guide

How TestPilot actually works

A plain-language walkthrough of everything TestPilot does — the original 3 test-case-generation inputs, the brand-new 4th input (a LangChain-powered knowledge assistant), why it was built the way it was, and how to extend it. Written so it makes sense even if you've never touched LangChain or RAG before.

Start here

The big picture: one app, four ways in

TestPilot is a chat app for QA work. You can talk to it in four different ways. The first three all end with the same result — new, freshly generated test cases. The fourth is different on purpose: instead of generating something new, it lets you ask questions about test knowledge that already exists.

Input 1

Type a user story

Paste a plain-English requirement. The app generates structured test cases from scratch.

Input 2

Attach a PRD file

Upload a requirements document (PDF/TXT/MD). Same generation pipeline, fed by the file instead of typed text.

Input 3

Connect a Jira ticket

Pull a ticket's Summary/Description/Acceptance Criteria automatically, review it, then generate.

Input 4 — NEW

Ask Knowledge Search

Ask a question about test plans or test cases you already have. No generation — just accurate answers, with sources.

The one-sentence version

Inputs 1–3 answer "help me write new test cases for this requirement." Input 4 answers "tell me what we already know" — and it's built on a completely different, independent technology (LangChain) from the other three (which run on a tool called Langflow). This guide explains both, but spends most of its time on Input 4, since that's what was actually built this session.

Inputs 1, 2, 3

The original 3 inputs: how test case generation works

All three of the original inputs — typed story, attached file, Jira ticket — funnel into the exact same generation engine, built in a tool called Langflow. Langflow is a visual drag-and-drop canvas for wiring together AI steps, instead of writing all the plumbing code by hand.

The two-call "Writer → Reviewer" pipeline

Rather than asking one AI to do everything in one shot, the flow uses two separate AI calls with two different jobs — because a single AI call has a practical limit on how much it can produce, and every extra rule you give it just makes it quietly skip something else to make room.

In plain English

Call 1 is like a diligent junior tester: given a requirement, they inventory every single detail (every table row, every button, every user type) and then write a test case for each one — no skipping, no summarizing.

Call 2 is a strict senior reviewer who re-reads the original requirement as if the junior's inventory didn't exist, catches whatever got missed or watered down, writes the missing test cases, adds the nasty edge cases (what happens if two things happen at once? what if someone tampers with a price?), and finally grades the whole set honestly with a coverage report.

How Jira tickets get in safely

The server.js Express backend holds your Jira API token — the browser never sees it. When you type a Jira ticket ID, the browser asks your own server, your server asks Jira, and only the clean Summary/Description/Acceptance Criteria come back to you for review before anything gets generated.

Input 4

The 4th input: Knowledge Search

This is the one built from the ground up this session. It's a chat panel that answers questions using your organization's own existing data — not the AI's general training knowledge, and not newly generated content.

Source 1

Test Plan

Confluence pages your QA team already wrote (test plans, chaos-testing sections, functional coverage). Ask a question, get an answer grounded in those real documents, with a link back to the source page.

Source 2

Test Cases

An existing library of real test cases in a database. Uses hybrid search — both keyword matching and meaning-based matching at once — to find the most relevant ones.

Why build this separately from Langflow?

Inputs 1–3 are about creating something new from a requirement. Input 4 is about retrieving and explaining something that already exists — a genuinely different job. Rather than force that into the existing Langflow flow, it was built as its own independent pipeline, in this app's own backend, using a different toolkit built specifically for exactly this job: LangChain.

Technically, this means: a completely separate code path (server.js's /api/knowledge/query route), a separate button and panel in the UI, and zero changes to the 3 original inputs or the Langflow flow they depend on.

How we got here

The journey: four real phases

Input 4 wasn't built in one pass. It went through four distinct, deliberate phases — each one adding a real capability, each one tested against real data before moving on.

Phase 0
Build it by hand first

Every piece — fetching Confluence pages, splitting text into chunks, turning text into searchable vectors, combining keyword + meaning search, asking the AI to answer — was written from scratch, with plain code calling Mistral's and MongoDB's raw APIs directly. This proved the idea worked and surfaced real bugs (a pagination bug that silently dropped pages, a formatting bug that leaked raw HTML into stored text, a recall bug where a big page's content never reached the AI).

Phase 1
Migrate everything to LangChain

Every hand-written piece was replaced with the equivalent standard LangChain building block — same behavior, verified against the same real data, but built on a shared, well-tested toolkit instead of custom one-off code. Two more real bugs were found and fixed along the way (a batch size too large for Mistral's API, and a field-mapping bug that silently dropped an ID for half the search results).

Phase 2
Give it a memory

Before this, every question was answered in total isolation — no memory of what you'd just asked. Phase 2 added real conversational follow-ups: ask "what discount types does it support?" right after asking about a specific feature, and it correctly figures out what "it" means.

Phase 2.5
Make the AI brand swappable

The part of the system that writes answers (not the part that searches) was made configurable — one setting switches it between Mistral and Google's Gemini, without touching anything else. Currently running on Gemini.

Before vs. after, concretely

  • Direct fetch() calls to Mistral's raw API, written and retried by hand
  • A custom-written text splitter (missed a case: one 5,778-character chunk never got split)

The toolkit, in plain words

What is LangChain, really?

Analogy: imagine building a car. You could forge your own bolts, wind your own electrical coils, and machine your own engine mounts from raw metal. Or you could use a catalog of standard parts that every mechanic recognizes, that are already tested, and that snap together in predictable ways. LangChain is that standard-parts catalog — but for building software that connects documents, search, and AI language models together.

Every one of the following concepts replaced something we had originally written by hand. Here's each one, explained simply, with what it replaced:

Document

A tiny, standard "shipping label" for a piece of text: the text itself (pageContent), plus a box of extra facts about it (metadata) — which page it came from, its title, its URL. Every LangChain tool expects text in exactly this shape, so once your data is in this shape, it works everywhere.

Replaced

Our own made-up object shape: { pageId, title, url, content }. Worked fine, but only we understood it.

Embeddings

A way to turn any piece of text into a list of ~1,000 numbers (a "vector") that captures its meaning. Two pieces of text about similar things end up with similar number-lists, even if they don't share a single word.

Replaced

Our own direct HTTP calls to Mistral's embedding endpoint, with hand-written batching and retry logic.

Vector store & Retriever

A vector store is where all those number-lists get saved (in our case, inside MongoDB Atlas). A retriever is the librarian: hand it a question, it instantly finds the documents whose meaning-numbers are closest to the question's meaning-numbers.

Replaced

A hand-written MongoDB "$vectorSearch" database query, repeated in two different files.

A custom Retriever (when the standard one doesn't fit)

Not everything has a ready-made LangChain piece. Our Test Cases source needed keyword search against a specific database index — and LangChain's built-in keyword retriever works entirely in-memory, which would have ignored our real database index completely. So we wrote one small custom class that plugs into LangChain's standard shape, while still doing the actual search our own way.

Key lesson

LangChain doesn't force everything into its own boxes — custom code and standard LangChain pieces sit side by side, as long as the custom piece speaks the same "shape" (a Document in, a list of Documents out).

EnsembleRetriever

Takes two (or more) retrievers' separate ranked lists of results and merges them into one combined ranking — rewarding anything that both searches agreed was relevant. This is the standard technique called Reciprocal Rank Fusion.

Replaced

A hand-written function that manually built a lookup map and did this same ranking math by hand.

PromptTemplate

A fill-in-the-blanks form for talking to an AI model — instead of gluing strings together by hand every time, you write the instructions once with placeholders ({question}, {excerpts}) and just plug in the real values each time.

Replaced

Manual JavaScript string concatenation to build the prompt text.

LCEL — chaining pieces together (.pipe())

Short for "LangChain Expression Language." It's the mechanism for snapping pieces together like Lego: prompt.pipe(model) means "take whatever the prompt produces, and feed it straight into the AI model" — instead of manually calling one function, taking its output, and manually feeding it into the next one.

Replaced

Manually calling fetch() with a hand-built request body, and manually digging the answer text out of the raw JSON response.

Chat model (swappable)

The actual AI "brain" that reads text and writes text back. Because every provider's chat model (Mistral, Gemini, and others) is wrapped in the exact same LangChain shape, swapping which one answers your questions is a one-line change — proven directly in this project.

Chat message history

A notebook that remembers a conversation's turns (who said what), scoped to one session, so a later question can refer back to an earlier one ("it", "that test case", "its priority").

Replaced

Nothing — this capability didn't exist at all before Phase 2. It's a new capability made straightforward specifically because LangChain has a standard piece for it.

History-aware retriever

A smart pre-step: before searching, it checks whether there's conversation history. If there's a vague follow-up ("what about its priority?"), it uses an AI call to rewrite it into a clear, standalone question ("What is TC_5170's priority?") before handing it to the retriever — because the retriever itself has no way to guess what "its" means.

The honest comparison

Why LangChain instead of a "simple" hand-rolled RAG?

A "simple" RAG (Retrieval-Augmented Generation) system is genuinely just five steps: turn your documents into number-lists → save them → turn the question into a number-list too → find the closest matches → stuff those matches into a prompt and ask the AI to answer. That's exactly what our very first, hand-rolled version already did. So what did switching to LangChain actually buy us? Here's the honest, evidence-backed answer — not marketing.

The honest caveat

LangChain didn't make everything automatically correct. We still had to discover — the hard way, by hitting real errors — that Mistral's embedding API has a stricter batch-size limit than the library's default, and that firing all requests at once triggers a real rate limit. LangChain gives you well-tested building blocks; it doesn't remove the need to actually test them against your real APIs and real data.

What actually happens

Step by step: asking a question and a follow-up

  1. You click "Knowledge," pick a source, type a question

    e.g. "What is the Test Plan for Tournament Ticket Discounting about?" A brand-new, private conversation ID is created for this thread.

  2. The browser sends the question to the server

    Along with which source (Test Plan or Test Cases) and that conversation ID.

  3. No history yet → the question goes straight to search

    Since this is the first question, there's nothing to rewrite — no extra AI call spent.

  4. The question is turned into meaning-numbers

    Via Mistral's embedding model — the exact same model used when the documents were first stored, so the numbers are comparable.

  5. The database finds the closest-matching chunks

    For Test Plan: pure meaning-based matching. For Test Cases: meaning-based and keyword matching, combined.

  6. A special check: did one document dominate the results?

    If several of the top matches all come from the same source page, that page's entire content is fetched — not just the sampled pieces — so nothing relevant gets silently left out.

  7. The AI writes an answer, strictly from those documents

    Told explicitly: answer only using what's here, and say so plainly if it's not enough — never guess.

  8. The answer + source links are saved into that conversation's memory

    Ready to be used if a follow-up comes next.

  9. You type a follow-up directly in the main chat box

    e.g. "what discount types does it support?" — no need to reopen the panel or pick the source again.

  10. The app recognizes this as a follow-up

    Because the very last message in the chat was itself a Knowledge Search answer — so it reuses the same conversation ID and source automatically.

  11. This time, there IS history — so the question gets rewritten first

    An AI call turns "what discount types does it support?" into something search can actually use, like "What discount types does Tournament Ticket Discounting support?" — using the memory from step 8.

  12. Search, dominant-page check, and answer-writing repeat — this time with memory

    The final answer-writing step also sees the conversation history, so it correctly understands what "it" meant when phrasing its reply.

Under the hood

Mistral vs. Gemini — what's actually swappable

One setting (CHAT_MODEL_PROVIDER) currently set to Gemini. But not everything is swappable, and the line between what is and isn't matters a lot.

Fixed — always Mistral

Embeddings (both moments)

Turning stored documents into meaning-numbers, and turning your live question into meaning-numbers. These two have to use the same model, or the numbers wouldn't be comparable at all — like measuring one thing in miles and the other in kilograms.

Configurable — Mistral or Gemini

Writing the final answer & rewriting follow-ups

Both of these happen after the real documents have already been found. They just read text and write text back — no meaning-numbers involved — so which AI brand does this job is a free choice.

Why Gemini, for now

Tested directly, side by side, on the same real question: comparable speed (~6.4–6.7 seconds), comparable answer quality. The deciding factor was practical — Gemini's larger context window gives more headroom for the "dominant page" case, where an entire long page's content might need to be handed to the AI at once, and it's already used elsewhere in this app (the Langflow side) for the same kind of work.

A real lesson learned live

A specific pinned model name (gemini-2.5-flash) turned out to be deprecated mid-session — it errored with a live "no longer available to new users" message. The fix: use gemini-flash-latest, an alias that always points to whatever Google currently recommends, instead of a fixed version number that can go stale.

Where this can go

What we could build next, on the same foundation

Reranking

A dedicated step that double-checks each search result's real relevance before it reaches the AI — we already saw evidence this would help (a "login authentication" search once returned test cases that only mentioned login as a side step, not cases actually about authentication).

RAG-driven test case generation

Instead of only answering questions about existing test cases, use them as grounding to help generate new ones in the same house style — bridging Input 4 back toward what Inputs 1–3 do.

Persistent conversation memory

Right now, follow-up memory lives only in the server's working memory and disappears on restart. It could be upgraded to a real, permanent store without changing how the rest of the system works.

A practical recipe

How to add a new knowledge source (e.g. "Corporate Test Cases" or "PRD")

Because everything follows the same standard LangChain shapes, adding a brand-new source is a repeatable recipe, not a redesign. Here's the exact playbook, based on how Test Plan and Test Cases were actually built.

  1. Decide: is the data already stored somewhere, or does it need ingesting?

    If it's a fresh source (like a new Confluence space), you'll need an ingestion step. If it's an existing, already-searchable database (like Test Cases was), you can skip straight to step 5.

  2. Write a fetcher for the raw data

    Pull the content from wherever it lives (an API, a file export, a database) into plain text.

  3. Convert to plain text if needed

    Strip out any source-specific formatting (like Confluence's or Jira's special markup) into clean, readable text — reuse an existing converter if the source format is similar to one already handled.

  4. Chunk it and embed it

    Use LangChain's RecursiveCharacterTextSplitter to break long text into ~1,000-character pieces, then MistralAIEmbeddings + MongoDBAtlasVectorSearch.fromDocuments() to turn them into meaning-numbers and store them — this is a one-time (or occasional) offline script, not something that runs per-question.

  5. Create the Atlas Search index

    One vector index per new collection, matching the same 1024-dimension shape Mistral produces. (Remember: a free-tier Atlas cluster caps the number of indexes — plan for this before building.)

  6. Write the retriever file

    Copy the shape of testplanRetriever.js (vector-only) or testcasesRetriever.js (hybrid) depending on whether you also want keyword search. Wire in getSessionHistory / wrapWithHistoryAwareness for free follow-up support — no new memory code needed.

  7. Register it in server.js

    Add one line to the source lookup table: { corporateTestCases: queryCorporateTestCases }.

  8. Enable it in the dropdown

    Remove disabled from that option in index.html — this is exactly what's already waiting for PRD.

  9. Test with real questions before trusting it

    Check retrieval quality, source-citation accuracy, and a follow-up question — the same verification approach used for every source in this guide.

Quick reference

Glossary — every term, one line each

RAG (Retrieval-Augmented Generation)
Finding real documents first, then asking an AI to answer using only those documents — instead of relying on what the AI happened to learn during training.
Embedding
Text converted into a list of numbers that represents its meaning.
Vector / vector search
Another name for that list of numbers, and the act of finding the closest-meaning matches to a given one.
Chunk
A smaller piece of a longer document, sized so its meaning stays focused and it fits comfortably into an AI prompt.
Hybrid search
Combining keyword search and meaning-based search, since each catches things the other misses.
Reciprocal Rank Fusion (RRF)
The specific, standard math for merging two ranked result lists into one fair combined ranking.
Retriever
Anything that takes a question and returns the most relevant documents.
LLM / Chat model
The AI model that reads and writes natural language (Mistral, Gemini, etc.).
Prompt
The actual text sent to an AI model, including instructions and context.
LangChain
A toolkit of pre-built, standard pieces for building RAG and AI-powered applications, so you don't build every piece from scratch.
Langflow
A different tool — a visual, drag-and-drop canvas for building AI workflows. Powers Inputs 1–3, untouched by this session's work.
Session / conversation memory
Remembering earlier turns of a conversation so later questions can refer back to them.
MongoDB Atlas
The cloud database used here both as normal storage and as a vector-search engine.
Confluence
Atlassian's documentation tool — where the Test Plan source's real content lives.
