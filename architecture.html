01 Overview

Three moving parts, one process.

The whole app is a single Node process (server.js) that does two unrelated jobs: it serves the static frontend in public/, and it proxies one endpoint to Jira Cloud so the browser never sees a Jira API token. Everything else — chat state, Markdown rendering, file upload, Excel export, conversation history — lives in one frontend script, public/app.js, with no framework and no bundler. The actual test-case generation happens outside this codebase entirely, in a Langflow flow the frontend calls directly over REST.

05 Request flows

The app has exactly three ways to start a generation. All three converge on the same Langflow run call and the same rendering path.

Text mode default

sequenceDiagram
  participant U as User
  participant UI as app.js
  participant LF as Langflow

  U->>UI: type story, press Send
  UI->>UI: buildRunPayload(text)
  UI->>LF: POST /api/v1/run/{FLOW_ID}\nx-api-key · session_id
  LF-->>UI: outputs[0].outputs[0].results.message.text
  UI->>UI: extractMessageText → renderMarkdown
  UI-->>U: assistant bubble with test-case table

File mode PDF / PRD

sequenceDiagram
  participant U as User
  participant UI as app.js
  participant LF as Langflow

  U->>UI: attach PDF (paperclip or drop)
  UI->>LF: POST /api/v2/files (multipart)
  alt v2 upload returns 404 — older Langflow
    UI->>LF: POST /api/v1/files/upload/{FLOW_ID}
  end
  LF-->>UI: uploaded file path
  UI->>LF: POST /api/v1/run/{FLOW_ID}\ntweaks[FILE_COMPONENT_ID].path
  LF-->>UI: message.text
  UI-->>U: rendered response

Jira mode imported ticket

sequenceDiagram
  participant U as User
  participant UI as app.js
  participant SRV as server.js
  participant J as Jira Cloud
  participant LF as Langflow

  U->>UI: enter ticket ID, Fetch
  UI->>SRV: GET /api/jira/:ticketId
  SRV->>J: GET /rest/api/3/issue/:id (Basic auth)
  J-->>SRV: summary, description (ADF), AC field
  SRV->>SRV: adfToText / fieldToText normalize
  SRV-->>UI: { id, summary, description, acceptanceCriteria }
  UI-->>U: editable "Imported" view
  U->>UI: edit fields, Generate Test Cases
  UI->>LF: POST /api/v1/run/{FLOW_ID}\ntweaks[PREFETCHED_STORY_COMPONENT_ID]
  LF-->>UI: message.text
  UI-->>U: rendered response

06 History & storage

No database. State lives in the browser and in Langflow.

The sidebar list is a thin index kept in localStorage under the key tcgen_sessions — an array of { id, title, createdAt, lastUsedAt }, titled from the first user message or attached filename. Opening a past conversation doesn't replay from that index; it re-fetches the real transcript from Langflow's own message store via GET /api/v1/monitor/messages?flow_id=…&session_id=…, so the index is a pointer, not the record of truth. Deleting a conversation calls the same monitor API before dropping the local entry. Theme and the active model override are separate small localStorage keys.

07 Config & secrets

Two config files, two trust levels.

FileVisibilityKeys
public/config.jsShips to the browserBASE_URL · FLOW_ID · API_KEY · MODEL_TWEAKS · FILE_COMPONENT_ID · PREFETCHED_STORY_COMPONENT_ID
.envServer-onlyPORT · JIRA_BASE_URL · JIRA_EMAIL · JIRA_API_TOKEN · JIRA_AC_FIELD_ID
AsymmetryThe Langflow API key is client-side by design — app.js calls Langflow directly, so API_KEY is readable in the browser. The Jira API token never takes that path: it lives only in .env on the server, which is the entire reason server.js's Jira proxy exists.

08 Spec of record

This isn't reverse-engineered — the spec is checked in.

CustomChat.md is the original build prompt the app was generated from: persona, hard constraints (no Langflow embedded-chat widget, config isolated from code), the exact API contract for text/file/Jira runs, and the UI requirements for every feature in the README's feature table. When behavior here looks deliberate rather than incidental — the two-step file upload with a legacy fallback, column-name-based Excel mapping, the auto-discovery fallback for component IDs — that's why: it was specified, not guessed.
